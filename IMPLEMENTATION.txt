
IMPLEMENTATION
==============

1. INTRODUCTION
---------------

This section describes the implementation of two core features in the project:
1) a multi-framework SQL query benchmark, and 2) an LLM-based date fruit
classification system. Both features use Groq large language models (LLMs) and
are designed to evaluate performance, accuracy, and explainability in
real-world tasks.

The first feature focuses on benchmarking two agent frameworks (CrewAI and
LangGraph) on structured SQL query generation and execution over a real
database.
The second feature focuses on using an LLM to analyze and classify
date fruits based on numerical feature vectors, combining standard machine
learning preprocessing with LLM-based reasoning.


2. FEATURE 1: SQL AGENT BENCHMARK SYSTEM
----------------------------------------

2.1 System Architecture
-----------------------

The SQL Agent Benchmark compares two agent orchestration frameworks, CrewAI and
LangGraph, using exactly the same configuration so the comparison is fair.
Both frameworks:
- Use the same LLM: Groq LLaMA-3.3-70B (temperature ≈ 0.1, max_tokens ≈ 1000)
- Connect to the same SQLite database: amazon_cleaned.db
- Answer the same set of 10 benchmark questions per iteration
- Run for N iterations (for example, N = 3) as configured in config.yaml

The architecture is configuration-driven. The architecture separates configuration, database connectivity, LLM integration, tool definitions, and metrics collection. Configuration is centralized in YAML, enabling experimentation without code changes.



2.2 Database Tool System
------------------------

To ensure both frameworks interact with the database in the same way, the
project defines three standard tools using LangChain’s SQL utilities:

1) List Tables Tool
   - Uses SQLDatabase.get_usable_table_names()
   - Returns the list of actual table names in the database
   - Prevents the agent from guessing or hard-coding table names

2) Get Schema Tool
   - Uses SQLDatabase.get_table_info_no_throw(table_names)
   - Accepts comma-separated table names
   - Returns column names, data types, and a few sample rows
   - Forces the agent to understand the schema before writing SQL

3) Execute SQL Tool
   - Uses SQLDatabase.run_no_throw(query)
   - Executes the generated SQL query
   - Returns results or an error message instead of raising an exception
   - Enables the agent to see its mistakes and try corrected queries

Typical tool execution pattern for each question:
1) User question
2) List Tables → discover available tables
3) Get Schema → inspect columns and data types
4) Generate SQL query based on the schema
5) Execute SQL → run the query and get the results
6) Extract the final numerical answer from the result

Per question, the agent usually makes:
- 3–5 tool calls (list, schema, execute, plus any retries)
- 2–4 LLM calls (depending on how many correction iterations are needed)


2.3 CrewAI Framework Implementation
-----------------------------------

CrewAI uses a role-based agent abstraction. In this project there is a single
agent with the role “Senior Data Analyst” that is responsible for answering
each SQL question end-to-end.

Key properties of the CrewAI setup:
- Agent role: Senior Data Analyst
- Goal: generate correct SQL, execute it, and return a clear numerical answer
- Tools: list_tables_tool, get_schema_tool, execute_sql_tool
- Process: sequential (Process.sequential)
- Manager LLM: the same Groq LLaMA-3.3-70B model is used to coordinate steps

Execution flow per question:
1) The crew is kicked off with the natural language question.
2) The agent first calls the list tables tool to discover available tables.
3) It then calls the get schema tool to inspect table structure and column
   names.
4) Using this schema knowledge, it generates a SELECT SQL query.
5) It calls the execute SQL tool to run the query.
6) If an error is returned (for example, wrong column name), the agent uses
   this feedback to refine the SQL and retries.
7) Once valid results are obtained, the agent extracts the required number
   (for example, a count or an average) and returns it as a concise answer.

Approximate timing characteristics:
- Per question: about 3–8 seconds total
  - 0.5–1.0 s: discovering tables
  - 0.5–1.0 s: getting schema
  - 1.0–2.0 s: generating SQL
  - 0.1–0.5 s: executing SQL
  - 0.5–1.0 s: formatting answer
  - +2–4 s extra if one or two retries are needed
- Per iteration (10 questions): roughly 30–80 seconds


2.4 LangGraph Framework Implementation
--------------------------------------

LangGraph models the same workflow as a state machine (graph). It uses a
TypedDict-based state and explicit nodes and edges to control the flow.

Graph structure:
- Nodes:
  - assistant: runs the LLM and decides whether to call tools or finish
  - tools: executes one or more tools and returns their outputs
- State:
  - messages: list of message objects (user, assistant, tool results)
- Edges:
  - START → assistant (initial request)
  - assistant → tools (if the assistant decides to call a tool)
  - tools → assistant (tool results are passed back)
  - assistant → END (when a final answer is produced)

The assistant node uses a carefully designed system prompt that enforces the
same discipline as in CrewAI:
- It must call list tables before using any table.
- It must call get schema to understand table structure.
- It must avoid making up tables or columns.
- It must ultimately return a single, clear numerical answer.

The tools node executes the LangChain tools and returns results or error
messages. Errors are wrapped as tool messages and added back to the state, so
the assistant can see them and correct its behavior.

Approximate timing characteristics:
- Per question: about 2–6 seconds total
  - 0.1–0.2 s: graph initialization and routing
  - 0.8–1.5 s: assistant reasoning and planning
  - 0.5–1.5 s: tool execution
  - 0.1–0.3 s: state updates
  - 0.2–0.5 s: final answer generation
  - +1–3 s if retries are needed
- Per iteration (10 questions): roughly 20–60 seconds


2.5 Metrics Collection and Analysis
-----------------------------------

The project uses a MetricsCollector to track detailed performance information
for each iteration and framework. For every iteration it records:
- Start and end time
- Number of API calls (LLM invocations)
- Individual API latencies
- Number of retries
- Total iteration duration
- Match percentage (accuracy compared to ground truth)

Key formulas:
- Iteration time:
  T_iter = T_end − T_start
- API latency for a single call:
  L_api = T_response − T_request
- Average API latency:
  L_avg = (Σ L_i) / n
  where L_i is the latency of call i and n is the total number of calls
- Accuracy (match percentage):
  Accuracy = (Correct / Total) × 100%

Data is stored in:
- CSV files: results_iter{N}_{Framework}.csv
  (question, predicted answer, expected answer, match flag)
- JSON files: metrics_{timestamp}_iter{N}.json
  (iteration, api_calls, api_latencies, avg_api_latency, match_percentage, etc.)
- PNG charts: metrics_{timestamp}_iter{N}.png
  (bar charts comparing iteration time, API calls, latency, accuracy)


2.6 Answer Extraction and Validation
------------------------------------

The benchmark expects most questions to have a numeric answer (for example, a
count or an average). The system:
- Uses a regular expression to extract the first numeric value (integer or
  decimal) from the LLM’s textual response.
- Converts that value into a float for comparison.
- Compares it against the ground truth values in expected_results.csv.

The validation pipeline:
1) Reads the expected answers from a CSV file.
2) Aligns each question’s predicted numerical answer with the expected one.
3) Counts how many answers match exactly.
4) Computes the accuracy percentage using the formula above.

If no number can be extracted from a response, that question is marked as
incorrect. This ensures metrics reflect practical performance, not just
successful responses.


3. FEATURE 2: DATE FRUIT CLASSIFICATION SYSTEM
----------------------------------------------

3.1 Data Pipeline and Preprocessing
-----------------------------------

The Date Fruit Classification system works on a structured dataset of 898
samples. Each sample represents a single date fruit and is described by 34
numeric features plus a class label.

High-level dataset characteristics:
- Samples: 898
- Features: 34 numeric features
- Target classes: 7 (BERHI, DEGLET, DOKOL, IRAQI, ROTANA, SAFAVI, SOGAY)

Feature groups:
- Geometric (for example: AREA, PERIMETER, MAJOR_AXIS, MINOR_AXIS)
- Shape descriptors (for example: ECCENTRICITY, SOLIDITY, COMPACTNESS)
- Texture (for example: ENTROPY, SKEWNESS, KURTOSIS)
- Color statistics (for example: MeanRR, MeanRG, MeanRB, MeanGR, MeanGG, MeanGB)

Preprocessing steps:
1) Split the dataset into features (X) and labels (y).
2) Perform a train–test split with 80% training and 20% test data:
   - 718 samples for training
   - 180 samples for testing
   - random_state = 42 for reproducibility
3) Apply feature standardization using:
   z = (x − μ) / σ
   where x is the original value, μ is the mean of that feature, and σ is the
   standard deviation. This produces features with approximately zero mean and
   unit variance, which makes them easier for the LLM to interpret and compare.


3.2 DateFruitAgent Architecture
-------------------------------

The DateFruitAgent wraps together scaling, LLM interaction, and benchmarking
logic into a single, reusable component. It uses:
- A Groq LLaMA-3.1-8B-instant model (low latency, suitable for per-sample
  analysis).
- A StandardScaler fitted on the training data to normalize features.
- An internal structure to record metrics such as times and predicted classes.

Main responsibilities:
- Convert raw feature rows into scaled vectors.
- Ask the LLM to analyze those vectors and explain important features.
- Ask the LLM to classify each sample into one of the 7 date fruit classes.
- Record timing and results for benchmarking.

Core methods:
- process_features(): prepares and scales a single sample’s features.
- analyze_features(): asks the LLM to analyze the scaled features and describe
  patterns and key attributes.
- get_classification(): asks the LLM to assign a class label and provide
  reasoning.
- batch_analyze(): orchestrates feature processing, analysis, and
  classification for multiple samples and aggregates metrics.


3.3 Two-Stage Analysis Process
------------------------------

The classification process is intentionally split into two logical stages:
1) feature analysis and 2) class prediction. This design increases
explainability.

Stage 1: Feature Analysis
- Input:
  - Scaled feature vector for one sample (34 values after z-normalization).
- Prompt content:
  - Names of the features and their scaled values.
  - Instructions to describe the fruit’s likely shape, size, texture, and
    color, and to highlight the most influential features.
- Output:
  - A qualitative explanation of the fruit’s characteristics.
  - Identification of features that point toward certain classes.
- Timing:
  - T_analysis = T_llm_response − T_llm_request
  - Typically around 0.5–1.5 seconds per sample.

Stage 2: Classification
- Input:
  - The same scaled feature vector.
  - An explicit list of the 7 allowed classes:
    BERHI, DEGLET, DOKOL, IRAQI, ROTANA, SAFAVI, SOGAY.
- Prompt content:
  - Request to classify the fruit into exactly one of these classes.
  - Instruction to start the answer with the class name, followed by a
    confidence score and reasoning.
- Output:
  - A predicted class label.
  - Confidence (0–100%) and textual reasoning.
- Class extraction:
  - A regex is used to detect the class name:
    (BERHI|DEGLET|DOKOL|IRAQI|ROTANA|SAFAVI|SOGAY)
  - If the regex finds a match, that is taken as the predicted class.
  - If not, the prediction is marked as UNKNOWN and logged.
- Timing:
  - T_classification = T_llm_response − T_llm_request
  - Typically around 0.3–1.0 seconds per sample.

Total time per sample:
- T_total = T_processing + T_analysis + T_classification
- Processing time (scaling) is negligible; most of the time is in LLM calls.
- Overall, each sample usually takes about 0.8–2.5 seconds to fully analyze
  and classify.


3.4 Performance Metrics and Benchmarking
----------------------------------------

The DateFruitAgent records detailed timing and classification statistics for
each batch of processed samples. For a batch of n samples (for example n = 5):
- Analysis times: T_analysis_i for sample i
- Classification times: T_class_i for sample i
- Total time per sample:
  T_total_i = T_analysis_i + T_class_i
- Total batch time:
  T_total = Σ T_total_i
- Average time per sample:
  T_avg = (Σ T_total_i) / n

It also tracks class distribution:
- Count per class:
  C_j = Σ 1(predicted_i = class_j)
  where 1(condition) is 1 if the condition is true, otherwise 0.
- Percentage per class:
  P_j = (C_j / n) × 100%

These metrics make it easy to see:
- How fast the system processes each sample.
- Whether some samples are significantly slower or faster than others.
- How the predicted classes are distributed (for example, whether the model is
  biased towards certain classes).


3.5 Output Generation and Reporting
-----------------------------------

Each run of the DateFruitAgent produces multiple outputs with timestamps to
ensure reproducibility and traceability:

1) JSON benchmark file
   - File name pattern:
     benchmark_llama-3.1-8b-instant_{timestamp}.json
   - Contains:
     - Model name and timestamp.
     - Number of samples processed.
     - Total and average processing time.
     - Lists of analysis times and classification times.
     - List of predicted classes.
     - Raw LLM responses (analysis + classification) for each sample.

2) Performance charts
   - Files:
     - performance_benchmark_{timestamp}.png
     - classification_distribution_{timestamp}.png
   - Show:
     - Time per sample (analysis, classification, total).
     - Average time line.
     - Bar chart of how many samples were assigned to each class.

3) Markdown report
   - File name pattern:
     date_fruit_analysis_report_{timestamp}.md
   - Includes:
     - Model configuration and run information.
     - Summary metrics (samples, total time, average time).
     - For each sample: predicted class, processing time, full LLM analysis
       text, and classification reasoning.


4. CROSS-FEATURE COMPARISON
---------------------------

4.1 Common Design Patterns
---------------------------

Both the SQL Agent Benchmark and the Date Fruit Classification system share
several important design principles:
- They both use Groq LLMs, but with different model sizes optimized for their
  tasks (70B for complex SQL reasoning, 8B for faster per-sample analysis).
- They target reproducibility by fixing random seeds and using clear
  configuration files.
- They prioritize explainability: the SQL system can generate queries step by
  step using tools, while the date fruit system explains why it chose a
  particular class.
- They collect detailed metrics to support benchmarking and comparison, rather
  than just returning answers.


4.2 Performance Characteristics
-------------------------------

SQL Agent Benchmark:
- 10 questions per iteration.
- 20–40 LLM calls per iteration (2–4 calls per question).
- Extensive use of tools and retries increases total runtime.
- Typical iteration time:
  - CrewAI: about 30–80 seconds.
  - LangGraph: about 20–60 seconds.

Date Fruit Classification:
- 5 samples per batch (configurable).
- 2 LLM calls per sample (analysis + classification).
- Total of 10 LLM calls per standard batch.
- Typical batch time: about 4–12.5 seconds.

In general, the SQL benchmark has higher overhead due to tool orchestration and
the need to query a live database, while the date fruit module is more direct
and lightweight, focusing only on vector-based reasoning and classification.

6. CONCLUSION
-------------

The implementation demonstrates how LLM-based agents can be applied to two
different problem types: structured SQL analysis and tabular data
classification. The SQL Agent Benchmark provides a framework to compare agent
orchestration libraries under identical conditions, while the Date Fruit
Classification system showcases an explainable approach to classification that
combines traditional preprocessing with LLM reasoning.

Together, these features illustrate a complete workflow: from configuration and
data preparation, through agent design and execution, to metrics collection,
visualization, and reporting. This makes the project suitable as both a
benchmarking tool and a learning resource for understanding modern AI agent
implementations.
